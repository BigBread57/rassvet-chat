# Design

## Context

См. `proposal.md` и пять спецификаций change. В репозитории пока нет приложения и сервиса. Доступны два Raspberry Pi 4B с OpenMANET 1.8; тестовый канал — 906 МГц, 4 МГц. Измерений пропускной способности именно этого стенда нет. Сервис должен работать на каждом узле; внешний сервер и Google-сервисы для первого этапа не требуются.

## Goals / Non-Goals

**Goals:**

- Получить воспроизводимую сборку и установку сервиса на оба тестовых узла и Android-клиента.
- Обеспечить административную выдачу доступа, закрытые комнаты, текст и вложения на двух связанных узлах.
- Сделать проверку доступа на сервере и фиксировать подтверждённые состояния доставки.

**Non-Goals:**

- Не проектировать в этом change алгоритм слияния данных после разделения сети, гарантии работы при разрыве, BLOS, голос и видео.
- Не считать заявленную ёмкость радиоканала доказанной без испытания стенда.

## Decisions

### 1. Один сервис на каждом Raspberry Pi

Оба узла запускают одинаковый сервис с локальной базой и хранилищем вложений. Android-клиент обращается к доступному доверенному узлу. Для первого этапа список двух узлов задаётся при выдаче доступа; отдельный сервер обнаружения не нужен. Это соответствует ADR 0001 и позволяет проверить полный путь «телефон — узел — узел — телефон». Альтернатива с одним центральным сервером нарушила бы принятое размещение сервиса.

### 2. Небольшой стек с локальным хранением

Сервис реализовать на Go с SQLite для учётных записей, прав, комнат, сообщений и метаданных; содержимое вложений хранить файлами на выделенном накопителе. Android-клиент реализовать на Kotlin с использованием стандартных Android API для выбора файлов и локального хранилища; QR-код считывать автономным декодером без Google-сервисов. Выбор обоснован доступностью сборки под Raspberry Pi и отсутствием отдельной СУБД. Альтернатива с внешней БД добавляет зависимый узел и обслуживание. Конкретные версии SDK, библиотек и формат пакета выбираются после проверки совместимости с целевыми устройствами и OpenMANET 1.8.

### 3. Выдача доступа и доверие

Администратор создаёт учётную запись в приложении через административный API узла выдачи и показывает одноразовый QR-код с короткоживущим кодом активации, адресами двух узлов и данными для проверки их подлинности. Телефон создаёт ключ в Android Keystore, передаёт открытый ключ при активации, после чего узел выдачи атомарно связывает учётную запись с этим ключом и гасит код. Активация проводится только на узле выдачи, чтобы два узла не приняли один код параллельно; результат затем передаётся второму узлу. Все клиентские и межузловые запросы идут по TLS с проверкой доверенных ключей. PIN блокирует доступ к приложению и локальным данным. Альтернатива с общим паролем и свободной регистрацией не обеспечивает привязку одного телефона.

### 4. Права проверяются на принимающем узле

Администратор создаёт комнаты и меняет членство и права. Узел проверяет роль и право для каждого запроса, включая получение списка комнат, историю, вложение по идентификатору, отправку и сохранение. Клиент скрывает недоступные действия, но не считается источником полномочий. Командир получает доступ к любой комнате; событие входа передаётся участникам. Альтернатива с проверкой только в интерфейсе оставляет прямой API-доступ к закрытым данным.

### 5. Связанные узлы обмениваются данными идемпотентно

Каждое изменение получает глобально уникальный идентификатор, время создания и автора. Узлы пересылают подтверждённые изменения по защищённому каналу, сохраняют их с ограничением уникальности и передают недостающие изменения при обычном повторном обмене, пока связь есть. Вложения передаются потоково и публикуются только после проверки размера и контрольной суммы. На этом этапе две копии подтверждаются только для данных, доставленных обоим связанным узлам; поведение разделённых частей выделено в следующий change. Альтернатива с трансляцией без локальной записи не даёт истории и защиты от повторной доставки.

### 6. Состояния, срок и загрузка вложений

Состояния «сохранено», «доставлено», «прочитано» обновляются по отдельным событиям; интерфейс не выводит доставку из успешного HTTP-ответа. Срок хранения считается от времени отправки, начально 3 дня, и применяется на узлах и к управляемому кешу клиента. Вложение до начального предела 100 МБ не скачивается автоматически: пользователь открывает его по запросу. Размер и срок задаются администратором. Альтернатива с автоматической загрузкой содержимого создаёт лишнюю нагрузку на узкий радиоканал.

## Risks / Trade-offs

- Узел выдачи недоступен при активации нового телефона → проводить первичную выдачу при доступности этого узла; работа ранее активированных телефонов от него не зависит.
- Скорость передачи файла 100 МБ на стенде неизвестна → передавать потоково, показывать ход передачи и проверить фактическое время на двух узлах. Требование о скорости не вводить без измерений.
- При потере связи между узлами этот этап не гарантирует синхронизацию изменений → испытание разрыва и восстановления вынести в следующий change.
- При компрометации телефона запрет сохранения не исключает внешнюю съёмку экрана → считать ограничение сохранения правилом интерфейса и прав доступа, не обещать защиту от внешней фиксации.
- Несовпадение часов влияет на срок хранения → сохранять время выдачи узлом, проверять синхронизацию часов при установке и не передавать истёкшие данные.

## Migration Plan

1. Проверить целевую архитектуру и свободное место на обоих узлах OpenMANET 1.8; подготовить накопители и резервные копии настроек.
2. Установить одинаковый пакет сервиса на каждый узел, настроить доверие между ними и проверить обмен без телефонов.
3. Установить подписанный APK на тестовые телефоны, выдать учётные записи и выполнить сквозной сценарий через два узла.
4. Для отката остановить сервис и вернуть сохранённые настройки узлов; локальные данные приложения сохранить отдельно до решения об их удалении.
