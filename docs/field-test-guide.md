# Проверка «Рассвета» на двух Raspberry Pi, двух Android-телефонах и MANET

Эта инструкция рассчитана на два Raspberry Pi с OpenMANET (далее **A** и **B**), Windows ПК и два Android-телефона. Выполняйте этапы по порядку: установите APK, проверьте приложение на локальном стенде ПК, настройте и проверьте MANET, установите сервис на Raspberry Pi, активируйте телефоны и проверьте сохранение данных. Если MANET уже настроена, в этапе 3 не меняйте работающие параметры: снимите их и выполните проверки связности.

> **Состояние проекта.** Локальный debug APK уже собран; при изменении исходников его пересобирают по [README](../README.md). Go-сервис и клиент проверялись локально, но установка на ваши OpenMANET и работа по реальному радиоканалу пока не подтверждены. В репозитории нет готового установочного пакета и проверенного автозапуска сервиса на OpenMANET. Голос, PTT и живое видео в текущий проверяемый этап не входят. Не отмечайте их как успешно испытанные.

## 0. Что подготовить

- Доступ по SSH к обоим Raspberry Pi с Windows ПК.
- Модель каждого Raspberry Pi и HaLow-модуля, версия прошивки OpenMANET, способ подключения радиомодуля (SPI/SDIO/USB). Они нужны для выбора совместимого образа и бинарного файла сервиса.
- Два USB-кабеля для подключения телефонов к ПК, если будете устанавливать APK через ADB.
- Доступ к отдельному накопителю для базы и вложений на каждом Pi. Сначала убедитесь, что накопитель действительно смонтирован.
- Время на всех четырёх устройствах должно быть выставлено правильно: подписанные запросы содержат время.
- Место для протокола: записывайте время опыта, ожидаемый результат, фактический результат, ошибки и снимки экрана.

В командах ниже `<PC_IP>`, `<A_IP>`, `<B_IP>`, `<DATA_A>` и `<DATA_B>` означают **измеренные на вашем стенде** адреса и пути. Угловые скобки в настоящие команды не вводят. Не берите адреса из примеров другого стенда.

Перед началом заполните:

| Параметр | Фактическое значение |
| --- | --- |
| IP Windows ПК в локальной Wi-Fi сети | |
| IP узла A в MANET | |
| IP узла B в MANET | |
| Версия OpenMANET на A и B | |
| Архитектура `uname -m` на A и B | |
| Путь отдельного накопителя на A и B | |
| SSID точки доступа A и SSID точки доступа B | |
| Версии Android телефонов 1 и 2 | |
| Модель Raspberry Pi и HaLow-модуля на A и B | |
| Роль A и B в OpenMANET (mesh gate / mesh point) | |
| Mesh ID, канал и ширина канала на A и B | |

## 1. APK: как собрать и установить

Соберите debug APK по [инструкции для разработки](../README.md#проверка-и-сборка). После сборки файл находится по пути от корня проекта:

```text
android\app\build\outputs\apk\debug\app-debug.apk
```

Это **debug APK** для испытаний. При отправке файла телефоны должны получить именно этот APK, а не `output-metadata.json` из того же каталога.

Чтобы зафиксировать, какой файл был отправлен, выполните в PowerShell из корня проекта:

```powershell
certutil -hashfile '.\android\app\build\outputs\apk\debug\app-debug.apk' SHA256
```

### Установка без ADB

Скопируйте APK на каждый телефон удобным вам способом. На телефоне откройте полученный APK, разрешите установку из этого источника, если Android попросит, и установите приложение **«Рассвет»**. Запишите, что установка прошла на обоих телефонах. Для дальнейшей работы доступ к Google Play приложению не нужен.

### Установка через USB и ADB

Если нужен контролируемый способ установки, установите на Windows [Android SDK Platform Tools](https://developer.android.com/tools/releases/platform-tools). На телефонах включите режим разработчика и **«Отладка по USB»**, подключите USB-кабель и подтвердите доверие к ПК на экране телефона.

Проверьте список устройств:

```powershell
adb devices
```

У обоих телефонов должен быть статус `device`. Возьмите их серийные номера из вывода и установите файл отдельно на каждый:

```powershell
adb -s <SERIAL_1> install -r '.\android\app\build\outputs\apk\debug\app-debug.apk'
adb -s <SERIAL_2> install -r '.\android\app\build\outputs\apk\debug\app-debug.apk'
```

Если на телефоне уже установлено приложение с другой подписью, обновление может быть отклонено. Удаление приложения стирает его локальные данные и привязку. Сначала сохраните результаты предыдущих опытов.

## 2. Быстрый сквозной тест без Raspberry Pi

Этот этап проверяет APK, активацию, PIN, комнаты, сообщения и файлы на двух телефонах. Он **не** проверяет радиосвязь MANET.

### 2.1. Запустите два тестовых узла на ПК

Узнайте IPv4 адрес Wi-Fi адаптера ПК:

```powershell
ipconfig
```

Ниже `<PC_IP>` — этот IPv4 адрес. В WSL откройте первый терминал:

```bash
cd /path/to/rassvet-chat/service
bash local-stand.sh run <PC_IP>
```

Скрипт запускает два экземпляра сервиса на портах **18443** и **18444**, печатает путь к `admin-ticket.json` и пишет журналы в каталог `~/.local/state/rassvet-chat-stand/<PC_IP>/`. Оставьте терминал открытым.

В отдельном окне PowerShell:

```powershell
cd 'C:\path\to\rassvet-chat\service'
python local-relay.py <PC_IP>
```

Оставьте открытым и это окно. Оба телефона подключите к той же Wi-Fi сети, что и ПК. Если Windows или WSL перезапускались и адрес изменился, заново определите адрес и перезапустите стенд с новым адресом.

Для проверки связи откройте на телефоне:

```text
https://<PC_IP>:18443/v1/peer/health
```

Браузер предупредит о тестовом самоподписанном сертификате. После продолжения ответ **HTTP 401** означает, что телефон достиг сервиса: этот служебный путь требует сертификат второго узла. Если соединения вообще нет, проверьте изоляцию клиентов Wi-Fi и входящий брандмауэр Windows для портов 18443 и 18444. Исключение сертификата в браузере не меняет проверку доверенного узла внутри приложения.

### 2.2. Активируйте телефон 1 как администратора

Код из `admin-ticket.json` действует **10 минут**. На телефоне 1 откройте **«Рассвет» → «Ручная настройка»**, вставьте всё содержимое `admin-ticket.json` в поле **«Данные активации JSON»** и нажмите **«Подключиться по JSON»**. Установите PIN из 4–12 цифр. Убедитесь, что открылся экран **«Чаты»**.

Если код истёк до активации, выполните в WSL:

```bash
cd /path/to/rassvet-chat/service
bash local-stand.sh ticket <PC_IP>
```

Используйте новый JSON. После успешной привязки администратора повторный выпуск его начального кода отклоняется.

### 2.3. Выдайте доступ телефону 2

На телефоне 1 откройте **«Настройки» → «Пользователи»**. Создайте обычного пользователя. Откройте его карточку и нажмите **«Выпустить ключ активации»**. На телефоне 2 выберите **«Сканировать QR-код»** и отсканируйте код с экрана телефона 1. Также доступны загрузка изображения QR и ручной ввод данных. На телефоне 2 установите свой PIN.

Выпускайте код, когда телефон 2 уже готов: код короткоживущий. Не отправляйте JSON активации в публичные QR-сервисы.

### 2.4. Проверьте комнату и переписку

На телефоне 1 откройте **«Настройки» → «Комнаты и права» → «Создать комнату»**. Добавьте пользователя телефона 2. Выдайте ему права чтения, отправки текста, добавления и сохранения вложений.

1. Отправьте короткое сообщение с телефона 1; убедитесь, что оно появилось на телефоне 2.
2. Ответьте с телефона 2; убедитесь, что ответ появился на телефоне 1.
3. Отправьте небольшой файл или фото. На втором телефоне проверьте карточку вложения и нажмите «Загрузить». При выданном праве сохранения файл должен появиться в системных «Загрузках»; после загрузки доступна одна кнопка «Передать».
4. Проверьте состояния сохранения, доставки и прочтения у отправителя.
5. На обоих телефонах откройте **«Настройки» → «Подключение»**. По очереди выберите узел 1 и узел 2; повторите отправку текста.

Если этот этап не проходит, сначала устраните ошибку здесь. Радиоканал MANET пока не участвует.

## 3. Настройте и проверьте MANET до установки сервиса

### 3.1. Определите состояние обоих узлов

Если оба Pi уже работают и передают данные, **не перепрошивайте их** ради этого теста. Запишите модель Pi, модель HaLow-модуля, версию OpenMANET и параметры радио на каждом узле. Ниже нужны два узла с IP-связью по HaLow и локальная Wi-Fi точка доступа на каждом для телефона.

На **A и B отдельно** подключитесь по SSH и выполните команды ниже. Они только читают состояние устройства:

```sh
tr -d '\000' < /proc/device-tree/model; echo
uname -m
cat /etc/openwrt_release
iw dev
ls /sys/bus/spi/devices /sys/bus/sdio/devices /sys/bus/usb/devices
dmesg | grep -Ei 'morse|halow|mm6108|mm8108' | tail -n 30
```

В первой строке ищите модель Raspberry Pi; `uname -m` показывает архитектуру процессора; в `/etc/openwrt_release` запишите версию и `DISTRIB_TARGET`; `iw dev` показывает работающие беспроводные интерфейсы. Каталоги `/sys/bus/...` и сообщения `dmesg` помогают определить, подключён ли HaLow-модуль через SPI, SDIO или USB и какой чип обнаружен. **Не считайте** само наличие устройств на шине доказательством модели HaLow: сопоставьте вывод с маркировкой модуля и названием уже установленного образа. Если `iw` или `dmesg` не показывает модель, перепишите маркировку с самого модуля; у меня нет точной информации о вашем радиомодуле без этих сведений.

Используйте результаты так:

| Полученные данные | Что с ними делать |
| --- | --- |
| Модель Pi | Для **новой** прошивки выберите в названии официального образа соответствующий `rpiX`: официальная таблица относит Pi 4/CM4 к `rpi4`, Pi 3B и Zero 2 W к `rpi3`. Для другой модели сверьтесь с актуальным списком образов. |
| Модель чипа и интерфейс HaLow | Для **новой** прошивки выбирайте образ с тем же семейством чипа (`mm6108`/`mm8108`) и интерфейсом (`spi`/`sdio`/`usb`). Если модель не установлена достоверно, образ не выбирайте. |
| `uname -m` и `DISTRIB_TARGET` | Перед сборкой `rassvetd` сопоставьте архитектуру, версию OpenWrt и системную библиотеку с целевым компилятором/SDK. Совпадения одного `uname -m` недостаточно для бинарного файла с SQLite/CGO. |
| Разные версии прошивки или настройки HaLow на A и B | Сначала приведите узлы к совместимой конфигурации по официальному мастеру и проверьте IP-связь. Не переносите между ними бинарный файл сервиса без проверки запуска на каждом. |

Сохраните вывод этих команд для протокола этапа 9. Значения `<A_IP>` и `<B_IP>` из них **не** заменяют код активации Android: код появится только после установки сервиса в этапе 5.

Если OpenMANET ещё не настроена, выполните первоначальную настройку по [официальной инструкции для Raspberry Pi](https://openmanet.github.io/docs/initial-setup/raspberry-pi) для **точной модели Pi и радиомодуля**. В [описании прошивок](https://openmanet.github.io/docs/firmware) объясняется, как выбрать образ по модели Pi, чипу и интерфейсу SPI/SDIO/USB. Без этих данных у меня нет точного имени образа для ваших устройств. Сохраните копию существующей конфигурации и данных до перепрошивки.

Для свежей установки официальный порядок такой:

1. Запишите выбранный образ OpenMANET на карту памяти согласно инструкции проекта и загрузите **один** Pi. На свежей прошивке подключите Windows ПК к Pi кабелем Ethernet и включите автоматическое получение IP на этом сетевом адаптере. Откройте `http://10.41.254.1` в браузере. Этот адрес относится к свежей прошивке **до** мастера настройки; после настройки адрес может измениться.
2. В мастере задайте узлу A роль **mesh gate** в режиме router и сохраните пароль администратора. Для автономного теста чата подключение к интернету не требуется. По официальной схеме текущей OpenMANET один mesh gate; второй узел настройте как **mesh point**.
3. Запишите выбранные в мастере HaLow **mesh ID, пароль (если используется), номер канала и ширину канала**. На узле B задайте те же значения. Для локальных точек доступа 2.4/5 ГГц задайте разные SSID, чтобы телефон 1 оставался на A, а телефон 2 — на B. Конкретные радиочастота, канал и ширина зависят от модуля, прошивки и местных ограничений; значения вашего стенда не подтверждены в репозитории.
4. Завершите мастер на каждом узле и дождитесь перезагрузки после резервирования адресов/DHCP. Переподключите ПК или обновите его DHCP-адрес. Узнайте **новый** IP A и B в интерфейсе OpenMANET и запишите их в таблицу этапа 0. Официальная [схема адресации](https://openmanet.github.io/docs/networking) описывает сеть клиентов `10.41.0.0/16`; не подставляйте в команды временный адрес свежей прошивки.

Для уже настроенных устройств начните с чтения параметров: подключитесь к их существующим точкам доступа или по Ethernet, откройте Web UI узлов и запишите роль, адрес, mesh ID, канал и ширину. В актуальной [документации Web UI](https://openmanet.github.io/docs/web-ui) управление доступно по `http://<IP_УЗЛА>:8080`, а параметры радио находятся в **Settings → Wireless**. Если интерфейс вашей установленной версии отличается, пользуйтесь её фактическим мастером и не меняйте параметры вслепую. Пароль Web UI/SSH относится к **OpenMANET**, он не является кодом входа в «Рассвет».

### 3.2. Подтвердите адреса и связь по радио

Подключите Windows ПК к точке доступа A. Откройте по SSH оба Raspberry Pi по их **фактическим адресам**. На **каждом** выполните:

```sh
uname -m
cat /etc/openwrt_release
ip -4 addr
ip -4 addr show br-ahwlan
ip -4 addr show bat0
df -h
cat /proc/mounts
batctl dc
```

Запишите вывод и определите IP каждого узла и реальные пути смонтированных накопителей. В официальной схеме клиентская сеть доступна через мост `br-ahwlan` и mesh-интерфейс `bat0`; если названия в установленной прошивке другие, найдите адреса в полном выводе `ip -4 addr`. Для `<A_IP>` и `<B_IP>` выберите **адреса самих узлов**, устойчивые после перезагрузки и достижимые с обоих телефонов, а не DHCP-адреса телефонов. `batctl dc` показывает известные mesh-узлы и клиентов; их наличие сверяйте с **актуальным** выводом, а не с примером адресов из документации. Если команда отсутствует в вашей прошивке, запишите это в протокол и проверьте связность следующими `ping`.

С A проверьте B:

```sh
ping -c 5 <B_IP>
```

С B проверьте A:

```sh
ping -c 5 <A_IP>
```

Запишите число потерянных пакетов и задержку. Проверьте в Web UI, что на обоих HaLow-модулях совпадают mesh ID, пароль, канал и ширина. В плане проекта записаны **906 МГц / 4 МГц**, но подтверждённого замера ваших узлов в репозитории нет. Зафиксируйте фактические значения и не меняйте настройки рабочего радио только по тексту плана.

Телефон 1 подключите к Wi-Fi узла A, телефон 2 — к Wi-Fi узла B. На время автономного опыта отключите на обоих мобильные данные. В свойствах Wi-Fi на каждом телефоне проверьте полученный IP-адрес; для схемы из актуальной официальной документации он должен быть в `10.41.0.0/16`. С телефона 1 откройте Web UI A и B по их записанным IP, затем повторите с телефона 2. Это проверяет доступ каждого телефона к **обоим** узлам: активация и переключение приложения требуют такой доступности. Если Web UI намеренно отключён, проверяйте доступ к сервису после шага 5.3. Пока нет базовой IP-связности A ↔ B, к установке чата не переходите.

**Контрольная точка:** известны реальные `<A_IP>` и `<B_IP>`; `ping` работает в обе стороны; телефон 1 и телефон 2 имеют доступ к обоим узлам. Если нет — сначала исправьте MANET по [разделу диагностики ниже](#8-что-делать-если-не-работает).

## 4. Получите исполняемый файл сервиса для ваших Pi

Это обязательная точка перед установкой. Сервис использует `github.com/mattn/go-sqlite3`, которому нужна сборка с C-кодом. В проекте пока нет проверенной команды сборки под конкретную архитектуру и системную библиотеку ваших OpenMANET.

На **каждом** Pi проверьте наличие инструментов:

```sh
command -v go
go version
command -v cc
cc --version
df -h
```

Если `go` или `cc` не найдены, этот вариант сборки на Pi не подходит; нужен совместимый с **вашей** прошивкой SDK/toolchain. Зафиксируйте вывод этапа 3.1, чтобы подобрать сборку под `DISTRIB_TARGET`, архитектуру, libc и CGO. У меня нет точной готовой команды SDK без этих значений. Если оба инструмента есть и версия Go не ниже указанной в `service/go.mod`, соберите прямо на каждом устройстве:

Сначала перенесите каталог `service` из проекта на **каждый** Pi. Например, из PowerShell в корне проекта (подставьте фактический SSH-логин вместо `<SSH_USER>`):

```powershell
scp -r '.\service' <SSH_USER>@<A_IP>:/root/
scp -r '.\service' <SSH_USER>@<B_IP>:/root/
```

Если входите не под `root`, выберите доступный вам каталог на Pi и замените путь `/root/service` также в следующей команде. Для первой сборки нужны доступные зависимости Go, указанные в `service/go.mod`; если Pi автономны и зависимостей на них нет, подготовьте совместимый бинарный файл вне Pi.

```sh
cd /root/service
CGO_ENABLED=1 go build -o rassvetd ./cmd/rassvetd
./rassvetd version
```

Если инструментов на Pi нет, нужна сборка с SDK/toolchain, соответствующим **фактически установленной прошивке**. У меня нет точной команды для этого случая без результатов `uname -m` и `/etc/openwrt_release` с ваших двух устройств. Не копируйте на Pi произвольный Linux ARM файл: одинаковая архитектура CPU не доказывает совместимость SQLite, libc и динамической загрузки.

Продолжайте только после успешного выполнения `./rassvetd version` на **обоих** Pi. Зафиксируйте хеш бинарного файла. Убедитесь по `df -h`, что для базы и вложений выбран отдельный накопитель, а не системный раздел OpenWrt.

**Контрольная точка:** один и тот же проверенный вариант сервиса запускается на A и B; известны пути к бинарному файлу и отдельным накопителям. Если сборка не проходит, сохраните `uname -m`, `/etc/openwrt_release`, версию Go, вывод `go build` и не начинайте шаг 5 с неподтверждённым бинарным файлом.

## 5. Ручная установка сервиса на два Pi

Проводите этот этап после подготовки совместимого бинарного файла. Перед изменениями сохраните резервную копию настроек обоих OpenMANET. В примерах `<DATA_A>` и `<DATA_B>` — каталоги на проверенных смонтированных накопителях. Каждый блок с `./rassvetd` выполняйте из каталога, где лежит проверенный бинарный файл (например, сначала `cd /root/service` в **каждом** новом SSH-окне). Проверьте на каждом Pi `date -u` и исправьте время до активации: запросы телефона подписаны с текущим временем. Каталоги идентичности `identity` перед вызовом `init-node` не создавайте: команда создаёт их сама.

### 5.1. Создайте идентичности

На A:

```sh
umask 077
mkdir -p <DATA_A>/rassvet
./rassvetd init-node node-a <DATA_A>/rassvet/identity <A_IP>
./rassvetd node-pin <DATA_A>/rassvet/identity/cert.pem
```

На B:

```sh
umask 077
mkdir -p <DATA_B>/rassvet
./rassvetd init-node node-b <DATA_B>/rassvet/identity <B_IP>
./rassvetd node-pin <DATA_B>/rassvet/identity/cert.pem
```

Запишите результаты `node-pin` как `<PIN_A>` и `<PIN_B>`. Через `scp` перенесите **только** `cert.pem` с A на B, а с B на A. На каждом узле сохраните сертификат другого под именем `<DATA_...>/rassvet/peer-cert.pem`. Закрытый `key.pem` между узлами не копируйте.

Например, из PowerShell на Windows ПК (подставьте реальные SSH-логины, адреса и пути; временные копии сертификатов сохраняются вне репозитория):

```powershell
Set-Location $env:TEMP
scp <SSH_USER_A>@<A_IP>:<DATA_A>/rassvet/identity/cert.pem '.\node-a-cert.pem'
scp <SSH_USER_B>@<B_IP>:<DATA_B>/rassvet/identity/cert.pem '.\node-b-cert.pem'
scp '.\node-a-cert.pem' <SSH_USER_B>@<B_IP>:<DATA_B>/rassvet/peer-cert.pem
scp '.\node-b-cert.pem' <SSH_USER_A>@<A_IP>:<DATA_A>/rassvet/peer-cert.pem
```

Проверьте перед продолжением: на A файл `peer-cert.pem` содержит сертификат B, а на B — сертификат A. Вычислите `./rassvetd node-pin <DATA_A>/rassvet/peer-cert.pem` на A и `./rassvetd node-pin <DATA_B>/rassvet/peer-cert.pem` на B: результаты должны совпасть соответственно с `<PIN_B>` и `<PIN_A>`. Это обнаружит перепутанные файлы без копирования закрытых ключей.

На обоих узлах создайте **одинаковый** файл `nodes.json`:

```json
[
  {"url":"https://<A_IP>:8443","tls_spki_sha256":"<PIN_A>"},
  {"url":"https://<B_IP>:8443","tls_spki_sha256":"<PIN_B>"}
]
```

Подставьте реальные IP и pin. Эти IP должны совпадать с адресами, использованными в `init-node`, и должны быть доступны телефонам. Сервис сверяет pin и имена/IP в сертификатах при запуске.

Создайте на Windows ПК в текстовом редакторе файл `$env:TEMP\rassvet-nodes.json` с этим JSON и **заменёнными** адресами и pin. Затем скопируйте один и тот же файл на оба Pi:

```powershell
scp "$env:TEMP\rassvet-nodes.json" <SSH_USER_A>@<A_IP>:<DATA_A>/rassvet/nodes.json
scp "$env:TEMP\rassvet-nodes.json" <SSH_USER_B>@<B_IP>:<DATA_B>/rassvet/nodes.json
```

На каждом Pi откройте полученный `nodes.json` и проверьте обе строки: URL A содержит `<A_IP>`, URL B — `<B_IP>`, а `tls_spki_sha256` совпадают с результатами `node-pin`. При замене IP в дальнейшем потребуется согласованно заменить URL и сертификат с соответствующим SAN; одним изменением JSON это не исправить.

### 5.2. Создайте базы и первого администратора

На A:

```sh
./rassvetd init-db <DATA_A>/rassvet/chat.db
./rassvetd init-admin <DATA_A>/rassvet/chat.db "Администратор" \
  <DATA_A>/rassvet/nodes.json \
  <DATA_A>/rassvet/identity/cert.pem \
  <DATA_A>/rassvet/peer-cert.pem > <DATA_A>/rassvet/admin-ticket.json
```

На B:

```sh
./rassvetd init-db <DATA_B>/rassvet/chat.db
```

На B **не** выполняйте `init-admin`: первый администратор должен попасть туда через межузловой обмен. Команду `init-admin` на A выполняйте перед первым запуском `serve`; так сервис включит начальную запись администратора в журнал обмена.

Файл `<DATA_A>/rassvet/admin-ticket.json` создаёт **сервис «Рассвет» на A**, а не OpenMANET. В нём находятся `code` (одноразовый код), `issuer` (адрес узла выдачи) и `nodes` (два URL и проверочные значения сертификатов). Для входа в Android нужны **все** эти поля. Пароль Wi-Fi, пароль Web UI и IP-адрес сами по себе учётную запись «Рассвета» не активируют. Не публикуйте JSON и не переносите с Pi `identity/key.pem`.

Если удобнее вводить данные вручную, на экране **«Ручная настройка» → «Или заполните поля»** значения из этого JSON соответствуют полям так:

| Поле Android | Значение из `admin-ticket.json` |
| --- | --- |
| «Одноразовый код» | `code` |
| «Адрес узла 1» и «Ключ узла 1» | `nodes[0].url` и `nodes[0].tls_spki_sha256` |
| «Адрес узла 2» и «Ключ узла 2» | `nodes[1].url` и `nodes[1].tls_spki_sha256` |
| «Код выдал» | Выберите узел, чей `nodes[].url` **точно равен** `issuer` |

После заполнения нажмите **«Подключиться вручную»**. Значения `tls_spki_sha256` — это **результаты команды `node-pin`**, а не пароль Wi-Fi, не PIN приложения и не отпечаток, показанный браузером. Ошибка даже в одном символе URL или ключа помешает активации.

### 5.3. Запустите сервис в двух SSH-окнах

На A:

```sh
./rassvetd serve <DATA_A>/rassvet/chat.db :8443 \
  <DATA_A>/rassvet/identity/cert.pem \
  <DATA_A>/rassvet/identity/key.pem \
  <DATA_A>/rassvet/nodes.json \
  <DATA_A>/rassvet/attachments \
  <DATA_A>/rassvet/peer-cert.pem node-b
```

На B:

```sh
./rassvetd serve <DATA_B>/rassvet/chat.db :8443 \
  <DATA_B>/rassvet/identity/cert.pem \
  <DATA_B>/rassvet/identity/key.pem \
  <DATA_B>/rassvet/nodes.json \
  <DATA_B>/rassvet/attachments \
  <DATA_B>/rassvet/peer-cert.pem node-a
```

Оставьте SSH-окна открытыми; ошибки будут видны в них. Сервис опрашивает другой узел каждые 10 секунд. Для штатной остановки нажмите `Ctrl+C`. Автозапуск после перезагрузки OpenMANET пока не подготовлен и не проверен.

**Проверка до активации телефона:** с каждого телефона откройте в браузере `https://<A_IP>:8443/v1/peer/health`, затем `https://<B_IP>:8443/v1/peer/health`. После предупреждения браузера о самоподписанном сертификате ожидается **HTTP 401**: служебный путь принимает только сертификат второго узла. Это подтверждает достижимость HTTPS, но **не** подтверждает вход в приложение. Если соединения нет, проверьте, что оба процесса `serve` продолжают работать, IP и порт верны, а MANET допускает соединение телефона с обоими Pi. Исключение сертификата в браузере не меняет доверие внутри приложения.

Код администратора в `admin-ticket.json` действует 10 минут. Если срок истёк **до привязки телефона**, на A выпустите новый код:

```sh
./rassvetd reissue-admin <DATA_A>/rassvet/chat.db \
  <DATA_A>/rassvet/nodes.json \
  <DATA_A>/rassvet/identity/cert.pem \
  <DATA_A>/rassvet/peer-cert.pem > <DATA_A>/rassvet/admin-ticket.json
```

После привязки администратора эта команда отклоняется. JSON содержит секретный одноразовый код; не добавляйте его в общий журнал или публичный чат.

## 6. Сквозной сценарий по настоящей MANET

Локальный стенд ПК и Pi используют **разные адреса и ключи узлов**. Активация телефона на ПК не переносится автоматически на Pi. Перед повторной установкой или очисткой приложения сохраните результаты этапа 2: удаление приложения сотрёт локальную привязку.

### 6.1. Первый вход телефонов через MANET

1. Убедитесь, что сервис запущен на A и B по шагу 5.3. Подключите телефон 1 к точке доступа A, телефон 2 — к точке доступа B. Отключите мобильные данные. Наличие соединения с Wi-Fi само по себе не создаёт учётную запись в приложении.
2. Получите данные активации с A. Например, в PowerShell на Windows ПК выполните `scp <SSH_USER_A>@<A_IP>:<DATA_A>/rassvet/admin-ticket.json "$env:TEMP\rassvet-admin-ticket.json"`, затем откройте файл командой `notepad "$env:TEMP\rassvet-admin-ticket.json"`. На телефоне 1 откройте «Рассвет» → **«Ручная настройка»**. Перенесите значения `code`, двух `url`, двух `tls_spki_sha256` и `issuer` в поля по таблице шага 5.2, затем нажмите **«Подключиться вручную»**. Если можете безопасно скопировать **весь JSON** на телефон, вместо отдельных полей вставьте его в **«Данные активации JSON»** и нажмите **«Подключиться по JSON»**. Не публикуйте JSON в чате или протоколе. Если код истёк, выпустите новый на A командой `reissue-admin` из шага 5.3 и используйте новый файл.
3. На телефоне 1 установите PIN из 4–12 цифр и нажмите **«Сохранить PIN»**. Проверьте, что открылся экран **«Чаты»**. Это завершает первоначальную активацию администратора на данном телефоне.
4. На телефоне 1 откройте **«Настройки» → «Пользователи»**, создайте обычного пользователя, откройте его карточку и нажмите **«Выпустить ключ активации»**. На телефоне 2 откройте «Рассвет» и нажмите **«Сканировать QR-код»**. Считайте код с экрана телефона 1. Если сканирование неудобно, на экране подключения телефона 2 доступны загрузка фото QR-кода и ручная настройка.
5. На телефоне 2 установите собственный PIN и нажмите **«Сохранить PIN»**. Проверьте, что открылся экран **«Чаты»**. Выпускайте ключ непосредственно перед этим шагом: он короткоживущий.

Телефон 2, подключённый к B, при активации обращается к `issuer` из QR-кода. Поэтому связь B ↔ A и доступ телефона 2 к A должны работать **до** сканирования. Если приложение уже было активировано на локальном стенде ПК, оно показывает экран PIN для прежней привязки: JSON для Pi не заменяет её. Для нового полевого опыта используйте отдельный телефон/профиль либо после сохранения результатов локального опыта очистите данные приложения и выполните активацию заново. Это удаляет локальную привязку и кеш; не делайте этого во время проверки сохранности данных.

При последующих запусках уже активированного приложения введите установленный **на этом телефоне PIN** и нажмите **«Открыть»**. Повторно вводить JSON или сканировать QR не требуется. После удаления приложения или очистки его данных локальная привязка исчезнет и первоначальную активацию придётся выполнить заново; использованный одноразовый код повторно не сработает.

**Контрольная точка:** на обоих телефонах открыт экран «Чаты», у каждого свой PIN и своя учётная запись. При ошибке активации сначала проверьте HTTPS-доступ к обоим Pi из шага 5.3, срок действия кода и правильность JSON/QR; расшифровка ошибок — в [этапе 8](#8-что-делать-если-не-работает).

### 6.2. Переписка и файлы

1. На телефоне 1 создайте закрытую комнату. Добавьте пользователя телефона 2 и права чтения, текста, добавления и сохранения вложений.
2. Отправьте текст A → B. Запишите время отправки и время появления на втором телефоне. Затем ответьте B → A.
3. Отправьте маленький файл A → B. Убедитесь, что сначала появилась карточка вложения, затем нажмите «Загрузить», найдите файл в системных «Загрузках» и проверьте его содержимое.
4. На телефоне 1 откройте **«Настройки» → «Подключение»**, выберите B и повторите отправку. На телефоне 2 выберите A и повторите.
5. Штатно остановите сервис на B, оставив A работающим. Проверьте работу телефона 1 через A. Снова запустите B с **той же** базой, дождитесь обмена и проверьте появление новых данных через B.
6. Отдельно разорвите **только связь A ↔ B**, оставив каждому телефону связь со своим Pi. Проверьте локальную работу каждой части, затем восстановите связь и зафиксируйте, какие новые данные синхронизировались.

Наличие старого сообщения на B во время разрыва не доказывает передачу через разорванную связь: для этого сценария отправляйте **новое** сообщение после разрыва.

### 6.3. Проверьте сохранение после перезапуска

Не удаляйте данные приложения и не выполняйте `init-node`/`init-admin` повторно. Эти команды создают идентичности и первоначальную учётную запись, а для проверки сохранности надо запустить **те же** узлы с **теми же** файлами. Стандартный срок хранения текста и вложений — **3 дня**, поэтому проводите проверку сразу после отправки, пока записи не истекли.

1. На телефоне 1 через A отправьте в комнату уникальный текст с текущей датой и небольшой файл с известным содержимым. На Windows ПК сохраните копию исходного файла и вычислите её SHA-256 командой `certutil -hashfile '<ПУТЬ_К_ИСХОДНОМУ_ФАЙЛУ>' SHA256`. Запишите текст, имя файла и хеш в протокол.
2. На телефоне 2 через B убедитесь, что новый текст и карточка файла появились. **Пока не нажимайте «Загрузить» на телефоне 2**: скачивание после перезапуска тогда проверит именно серверные файлы, а не уже загруженную копию на телефоне.
3. На A выполните `df -h <DATA_A>` и `ls -ld <DATA_A>/rassvet/chat.db <DATA_A>/rassvet/attachments`; на B — такие же команды с `<DATA_B>`. Проверьте, что файлы находятся на выбранном смонтированном накопителе. Файлы вложений в каталоге сервиса названы по ID, а не по исходному имени; для списка выполните `ls -l <DATA_A>/rassvet/attachments` на A и соответствующую команду на B. Наличие файлов само по себе не доказывает читаемость через приложение — следующие шаги обязательны.
4. Остановите **оба** процесса `serve` через `Ctrl+C`. Запустите их снова командами шага 5.3 с теми же путями к базе, сертификатам, `nodes.json` и каталогу вложений. Если проверяете перезагрузку Pi, перезагрузите устройства и снова запустите `serve` вручную: автозапуск пока не настроен.
5. Закройте и снова откройте приложение на обоих телефонах, введите их PIN. На телефоне 2 выберите B в **«Настройки» → «Подключение»**, откройте комнату и найдите уникальный текст и карточку файла. Нажмите «Загрузить», проверьте файл в системных «Загрузках» и сравните его SHA-256 с исходным. Если на телефоне нет средства вычисления хеша, скопируйте скачанный файл на Windows ПК и выполните `certutil -hashfile '<ПУТЬ_К_СКАЧАННОМУ_ФАЙЛУ>' SHA256`.
6. Выберите A на телефоне 2 и повторно проверьте тот же текст и карточку. Отправьте новое сообщение через B и убедитесь, что оно появилось через A. Запишите отдельно результат для **каждого** узла. Если после рестарта работает только один узел, проверьте журнал `serve`, пути данных и межузловую связность.

Успех этого опыта означает, что **неистёкшие** данные пережили перезапуск на вашем стенде и файл сохранил хеш. Он не подтверждает сохранность после удаления приложения, истечения срока хранения или потери накопителя.

Сохранённый в системные **«Загрузки»** файл — отдельная копия вне управляемого кеша приложения. Уборка по сроку хранения на узлах не удаляет эту копию из «Загрузок»; при необходимости удалите её вручную после испытания.

### Испытание файла 100 МБ

Проводите его отдельно после успешного маленького файла. Сохраните исходный файл и вычислите его SHA-256. Отправьте его с телефона 1 через A, дождитесь появления через B, скачайте на телефоне 2 и сравните SHA-256 скачанного файла с исходным. Запишите фактическое время каждого этапа, ошибки и результат повторения после обрыва. Этот опыт показывает результат только для вашей двухузловой топологии; не переносите его на десять узлов или четыре радиоперехода без отдельного измерения.

## 7. Проверки доступа и отказов

После основного сценария выполните отдельные опыты. Для каждого записывайте **фактический** результат, а не только ожидаемый.

| Проверка | Действие | Что должно быть видно |
| --- | --- | --- |
| PIN без сети | Закройте приложение, отключите сеть, откройте снова; введите неверный, затем верный PIN | История закрыта до верного PIN |
| Одноразовый код | Повторно примените уже погашенный код к другому ещё не активированному телефону | Новая привязка отклонена |
| Закрытая комната | Уберите у пользователя право чтения; после доставки изменения откройте комнату | История и файлы не открываются |
| Отправка текста | Уберите право отправки текста | Следующая отправка отклонена |
| Вложение | Уберите право добавления, затем право сохранения | Соответствующие действия недоступны |
| Смена узла | Остановите выбранный узел, переключитесь на второй доверенный узел | Приложение продолжает работу через доступный узел |
| Перезапуск сервиса | Остановите и запустите его с той же базой и каталогом вложений | Неистёкшие данные остались |
| Срок хранения | На отдельном тестовом наборе задайте сокращённый срок через административный API | После истечения данные не выдаются на обоих узлах; приложение не показывает их как действующие. Копия, ранее сохранённая в системные «Загрузки», остаётся до ручного удаления |
| Чужой сертификат | Используйте отдельный тестовый адресат с другим ключом | Приложение отклоняет соединение |

Не публикуйте действующие QR-коды, JSON активации, PIN и закрытые ключи в скриншотах и журналах.

## 8. Что делать, если не работает

Идите сверху вниз: **радиосеть → IP → HTTPS сервиса → активация → права → сохранение**. После каждого исправления повторите только провалившуюся контрольную точку. Записывайте точный текст ошибки и время; не заменяйте диагностикой через мобильный интернет проверку MANET.

| Признак | Что проверить и сделать |
| --- | --- |
| ПК или телефон не подключается к Wi-Fi узла | Убедитесь, что выбран SSID нужного Pi и клиент получил IP. После мастера OpenMANET переподключите Wi-Fi для нового DHCP-адреса. Проверьте питание Pi и его точку доступа. |
| A и B не видят друг друга | На обоих узлах повторите `ip -4 addr`, `batctl dc`, `ping -c 5 <АДРЕС_ДРУГОГО_УЗЛА>`. Сверьте mesh ID, пароль, канал и ширину в настройках HaLow; посмотрите топологию и журналы OpenMANET. Если есть случайные перезагрузки или пропадание радио, проверьте питание и кабели. Не меняйте адреса и радионастройки наугад. |
| Телефон видит свой Pi, но не второй | Проверьте IP телефона и открытие Web UI **обоих** узлов с этого телефона. Затем повторите `ping` между A и B. Пока нет сквозной IP-связности, активация по QR с другого узла и межузловой обмен не будут проверены. |
| `serve` завершился сразу | Читайте сообщение об ошибке в том же SSH-окне. Проверьте, что `./rassvetd version` запускается, накопитель смонтирован, пути к базе/сертификатам/`nodes.json` верны, `peer-cert.pem` содержит сертификат другого узла, pin совпадает, а IP в сертификате совпадает с URL. Для каталога `attachments` сервис требует права `0700`. |
| Оба `serve` работают, но браузер не открывает `https://<IP>:8443/v1/peer/health` | Сначала проверьте IP и порт, затем доступность узла с того же телефона, сетевые правила OpenMANET и вывод процесса `serve`. Ответ **401** после TLS-подключения для этого адреса нормален; ошибка соединения или TLS до HTTP-ответа означает, что проверка доступности не пройдена. |
| На телефоне открыт PIN вместо активации к Pi | Приложение уже привязано к прежнему стенду. Сохраните результаты того опыта и используйте отдельный профиль/телефон либо очистите данные приложения перед новой активацией. Сам PIN не переключает старую привязку на новые сертификаты и адреса. |
| Активация не проходит | Убедитесь, что используется **полный** свежий JSON `admin-ticket.json` или QR нужного пользователя, а телефон достигает адреса `issuer`. При истечении начального кода до привязки выполните `reissue-admin` на A; после привязки он уже не выдаётся. Использованный одноразовый код повторно не применяют. Сверьте время на телефоне и Pi. |
| После PIN нет комнат или действие отклонено | Убедитесь, что на телефоне 1 создана комната, пользователь телефона 2 добавлен и получил нужные права. `401` у обычного API-запроса означает проблему с привязкой/подписью или временем, `403` — отказ в действии, `404` для закрытой комнаты может означать отсутствие права чтения. Сверьте фактический выбранный узел. |
| Сообщение есть на A, но не появляется через B | Проверьте связь A ↔ B, что оба `serve` продолжают работать, и сообщения `peer sync:` в их SSH-окнах. Подождите очередного обмена (период опроса — 10 секунд), обновите комнату на B и повторите. Не выдавайте старое, ранее синхронизированное сообщение за успешную доставку нового. |
| Вложение не отправляется или не скачивается | Проверьте права `add_attachment`, `read`, `save_attachment`, размер файла (начальный максимум — 100 МиБ), свободное место и состояние накопителя на обоих Pi. Ошибка `413` означает превышение предела, `422` — несовпадение SHA-256. Скачивание требует нажатия «Загрузить»; при праве сохранения файл появляется в системных «Загрузках». |
| После перезапуска нет прежних сообщений/файлов | Проверьте, что сервис запущен с **тем же** `chat.db` и каталогом `attachments` на смонтированном накопителе, выбран правильный узел и данные ещё не истекли. Начальный срок — 3 дня; истёкшие записи сервис удаляет. Не запускайте `init-admin` повторно и не очищайте данные приложения как способ «починить» сохранность. |
| При выборе или передаче файла появляется экран PIN | Запишите версию APK и точные действия; проверьте, что на телефоне установлен текущий APK из этапа 1. Обычный выход в системный выбор файла или окно передачи не должен сам по себе прерывать разблокированную сессию. Сохраните снимок экрана и журнал Android для воспроизведения ошибки. |

Для диагностики OpenMANET используйте также [официальные рекомендации](https://openmanet.github.io/docs/troubleshooting) и [описание сети](https://openmanet.github.io/docs/networking). Если используется ADB, снимите после ошибки журнал телефона командой `adb -s <SERIAL> logcat -d -t 500` в PowerShell; удалите из передаваемого журнала действующие коды активации и другие секреты. Если нет совместимого бинарного файла для Pi или неизвестны модель радиомодуля и установленная прошивка, у меня нет точной команды сборки/настройки для этих устройств: зафиксируйте факты из этапов 0, 3 и 4 и не отмечайте полевой тест как пройденный.

## 9. Протокол результата

Для каждого опыта заполните одну строку:

| № | Время | Сценарий | Телефон и выбранный узел | Ожидалось | Получено | Журнал/скриншот | Итог |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | | | | | | | |

К протоколу приложите вывод команд этапа 3.1 с обоих Pi, адреса устройств, реальные параметры радио, результаты `ping`, хеши APK и бинарного файла, а также времена и хеши опыта с файлом 100 МБ. Если какой-то этап не выполнен из-за отсутствия совместимой сборки или иной причины, запишите **«не проверено»**, не «пройдено».
