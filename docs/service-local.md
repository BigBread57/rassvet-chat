# Локальный запуск сервиса на Windows через WSL

Текущий проект расположен в `D:\Work\rassvet-chat`. На этом Windows ПК WSL Ubuntu видит его как `/mnt/d/Work/rassvet-chat`; в Ubuntu доступен Go 1.22.2, а в Windows установлен Python. Основной сценарий ниже запускает два тестовых узла в WSL и открывает их Android-телефонам через Windows. Проверка реальных Raspberry Pi и радиоканала MANET описана отдельно в [полевой инструкции](field-test-guide.md).

Команды в блоках `sh` и `bash` выполняются **в WSL Ubuntu**; команды в блоках `powershell` — **в PowerShell Windows**. Для тестов сервиса откройте PowerShell, выполните `wsl -d Ubuntu`, затем:

```sh
cd /mnt/d/Work/rassvet-chat/service
go test ./...
go build -o rassvetd ./cmd/rassvetd
./rassvetd version
./rassvetd init-node node-a /path/to/private-node-a <адрес-node-a>
./rassvetd init-node node-b /path/to/private-node-b <адрес-node-b>
./rassvetd node-pin /path/to/private-node-a/cert.pem
./rassvetd node-pin /path/to/private-node-b/cert.pem
```

Последующие команды с `/path/to/...` — пример ручной настройки Linux-узлов, а не готовая команда для этого ПК. Для Windows-стенда используйте раздел «Проверка на ПК и телефонах» ниже: скрипт сам создаёт ключи, базы и `nodes.json`.

Каталоги идентичностей создаются с правами `0700`, ключи — `0600`. Значения `node-pin` вставляются в файл `nodes.json` на обоих узлах:

```json
[
  {"url":"https://node-a:8443","tls_spki_sha256":"<pin node-a>"},
  {"url":"https://node-b:8443","tls_spki_sha256":"<pin node-b>"}
]
```

Перед запуском сервис сверяет оба значения `tls_spki_sha256` с локальным сертификатом и сертификатом настроенного второго узла, а имя или IP-адрес каждого URL — с полем SAN соответствующего сертификата. `init-node` нужно вызвать с именем или IP-адресом, используемым в `nodes.json`. Повторяющийся ключ или несовпадение адреса и сертификата останавливает запуск и выдачу кода активации.

На узле выдачи:

```sh
./rassvetd init-db /path/to/private-data/chat.db
./rassvetd init-admin /path/to/private-data/chat.db "Администратор" /path/to/nodes.json /path/to/private-node-a/cert.pem /path/to/private-node-b/cert.pem
./rassvetd serve /path/to/private-data/chat.db :8443 /path/to/private-node-a/cert.pem /path/to/private-node-a/key.pem /path/to/nodes.json /path/to/private-data/attachments /path/to/private-node-b/cert.pem node-b
```

На втором узле аргументы сертификата и ключа меняются на `private-node-b`, а последние два аргумента — на сертификат `private-node-a` и `node-a`. Второй узел запускается с отдельной базой без повторной команды `init-admin`: запись первого администратора передаётся из базы узла выдачи. Каждый узел принимает запросы `/v1/peer/*` только с сертификатом настроенного второго узла. Обычные Android-запросы не требуют клиентского TLS-сертификата, но требуют подпись устройства. Локальный тест `go test ./internal/nodetls -run TestOptionalPeerServer` проверяет доверенный, обычный клиентский и подменённый сертификаты. Служебный запрос `GET /v1/peer/health` возвращает идентификатор узла только после взаимной проверки TLS.

Сервис опрашивает второй узел каждые 10 секунд и сохраняет курсор после успешной записи страницы. Тест `TestConfigurePeerSeedsAdminCreatedBeforeServe` проверяет запись первого администратора в журнал после `init-admin`; повторный запуск не создаёт вторую запись. В локальном тесте `go test ./internal/api -run TestPeerSyncAndRetry` проверены передача учётных записей, привязки, комнаты, прав, текста, подтверждений и файла с проверкой SHA-256, а также повтор и краткий сбой. Измерений на радиоканале нет.

Команда `serve` обрабатывает SIGTERM и SIGINT: останавливает новые HTTP-запросы, отменяет межузловой обмен и ждёт текущие запросы до 30 секунд. После тайм-аута соединения закрываются; прерванную загрузку клиент может повторить с тем же идентификатором. Если после аварии файл уже записан, но метаданные ещё не появились в базе, повтор с тем же размером и SHA-256 завершает публикацию; несовпадающий файл отклоняется. Локально проверены ответ API, остановка по SIGTERM с кодом 0 и повторный запуск с той же базой. Автозапуск и остановка через менеджер сервисов OpenMANET ещё не проверены.

`init-admin` печатает готовый JSON с кодом, адресом узла выдачи и ключами двух узлов. На первом телефоне нужно открыть «Рассвет» → **«Ручная настройка»**, вставить JSON в поле **«Данные активации JSON»** и нажать **«Подключиться по JSON»**. Код действует 10 минут, а в базе хранится только его хеш. Если код истёк до привязки администратора, локальная команда `./rassvetd reissue-admin /path/to/private-data/chat.db /path/to/nodes.json /path/to/private-node-a/cert.pem /path/to/private-node-b/cert.pem` выдаёт новый JSON и аннулирует прежний код. После привязки она отклоняется. `init-db` можно выполнить повторно. Сервис запускается по TLS 1.3; команда установки и автозапуска на OpenMANET ещё не проверена.

После активации администратора доступны подписанные запросы из [контракта API](api.md): создание пользователя, выдача его кода активации, создание комнаты и выдача прав. `POST /v1/admin/users/{id}/activation` возвращает код и данные доверия для QR; код можно выдать повторно до привязки телефона, при этом предыдущий неиспользованный код аннулируется. `GET` и `PUT /v1/admin/settings` читают и меняют срок хранения и предел вложения. Аргумент `attachments-dir` команды `serve` — отдельный каталог вложений с правами `0700`; сервер создаёт его при необходимости. Файлы создаются с правами `0600`. Сервис удаляет истёкшие сообщения и вложения при запуске и затем каждую минуту; API скрывает их сразу после истечения срока.

## Android APK

**APK уже собран** и лежит в Windows по пути `D:\Work\rassvet-chat\android\app\build\outputs\apk\debug\app-debug.apk`. Повторная сборка для этой проверки не нужна. Перед отправкой проверьте именно отправляемый файл в PowerShell:

```powershell
Get-Item 'D:\Work\rassvet-chat\android\app\build\outputs\apk\debug\app-debug.apk'
Get-FileHash 'D:\Work\rassvet-chat\android\app\build\outputs\apk\debug\app-debug.apk' -Algorithm SHA256
```

Скопируйте APK на оба Android-телефона и установите. Это debug APK для испытаний, не подготовленный релизный пакет. Если используете Android SDK Platform Tools и USB-отладку, проверьте номера устройств через `adb devices`, затем выполните в PowerShell:

```powershell
adb -s <SERIAL_1> install -r 'D:\Work\rassvet-chat\android\app\build\outputs\apk\debug\app-debug.apk'
adb -s <SERIAL_2> install -r 'D:\Work\rassvet-chat\android\app\build\outputs\apk\debug\app-debug.apk'
```

При несовпадении подписи с уже установленным экземпляром Android отклонит обновление. Удаление приложения стирает его локальные данные и привязку; сначала сохраните результаты предыдущей проверки.

Если **позже** понадобится новая сборка, стандартная команда на Windows при установленном Android SDK — `cd D:\Work\rassvet-chat\android`, затем `.\gradlew.bat :app:assembleDebug`. Для текущего WSL-окружения использовалась команда из `/mnt/d/Work/rassvet-chat/android`: `ANDROID_HOME=/opt/android-sdk ./gradlew --init-script gradle/offline-wsl.init.gradle -Pandroid.aapt2FromMavenOverride=/opt/android-sdk/build-tools/36.0.0/aapt2 :app:assembleDebug`. Вариант с `--offline` требует полного локального кеша зависимостей и раньше завершался ошибкой из-за отсутствующей версии `androidx.compose.ui:ui-tooling-preview`. Сборка на чистой Windows-машине и установка на телефон пока не подтверждены протоколом испытаний.

## Проверка на Windows ПК и двух телефонах без Raspberry Pi

1. В PowerShell выполните `ipconfig` и найдите **IPv4 Wi-Fi адаптера**, к сети которого подключены телефоны. Ниже он обозначен `<PC_IP>`. Не используйте адрес WSL или виртуального адаптера.
2. В первом окне PowerShell выполните `wsl --status` и убедитесь, что дистрибутив WSL по умолчанию — Ubuntu. Затем откройте его командой `wsl -d Ubuntu`. Скрипт Windows-переходника получает IP именно дистрибутива **по умолчанию** через `wsl.exe hostname -I`; если по умолчанию выбран другой дистрибутив, переходник направит трафик не туда.
3. В открывшемся WSL запустите стенд:

   ```bash
   cd /mnt/d/Work/rassvet-chat/service
   bash local-stand.sh run <PC_IP>
   ```

   Скрипт собирает сервис, создаёт две разные идентичности с IP компьютера в обоих сертификатах, две базы и запускает узлы на портах **18443** и **18444**. Данные и журналы лежат в `~/.local/state/rassvet-chat-stand/<PC_IP>/`: в том числе `admin-ticket.json`, `a.log`, `b.log` и `nodes.json`. Первый код администратора действует 10 минут. Окно WSL оставьте открытым.

4. Во втором окне **PowerShell Windows** запустите переходник:

   ```powershell
   cd D:\Work\rassvet-chat\service
   python local-relay.py <PC_IP>
   ```

   Ожидаются две строки вида `<PC_IP>:18443 -> <WSL_IP>:18443` и `<PC_IP>:18444 -> <WSL_IP>:18444`. Переходник передаёт TCP без изменения TLS. Его окно также оставьте открытым.

Если код истёк до активации администратора, во **втором окне WSL** выполните:

```bash
cd /mnt/d/Work/rassvet-chat/service
bash local-stand.sh ticket <PC_IP>
```

Используйте новый JSON. После успешной привязки администратора повторная выдача кода отклоняется. Если WSL перезапустился и его IP изменился, остановите Windows-переходник сочетанием `Ctrl+C` и запустите заново. Для остановки всего стенда нажмите `Ctrl+C` в обоих основных окнах. При смене Wi-Fi сети и `<PC_IP>` запустите стенд для нового адреса: сертификаты старого адреса не подойдут.

С телефона, подключённого к той же сети Wi-Fi, открыть `https://<IPv4>:18443/v1/peer/health`. Браузер предупредит о самоподписанном тестовом сертификате; ответ HTTP 401 после продолжения означает, что TCP и TLS доступны. Этот адрес требует сертификат второго узла, поэтому обычный браузер не получает 200. Если соединение не устанавливается, проверить изоляцию клиентов Wi-Fi и входящий брандмауэр Windows. Открывать входящие порты только для двух тестовых портов и своей подсети. При проверке с телефона Android-приложение сверяет ключ узла из кода активации и не использует исключение браузера для сертификата.

Корневой адрес `https://<IPv4>:18443/` показывает только сообщение о работающем узле. Это адрес API, а не веб-версия чата: для входа нужен Android-клиент и одноразовый код активации.

На первом телефоне откройте «Рассвет» → **«Ручная настройка»**, вставьте содержимое свежего `admin-ticket.json` в поле **«Данные активации JSON»**, нажмите **«Подключиться по JSON»** и установите PIN. Затем на первом телефоне откройте **«Настройки» → «Пользователи»**, создайте обычного пользователя, откройте его карточку и выпустите QR-код. На втором телефоне отсканируйте QR-код и установите отдельный PIN. На первом телефоне через **«Настройки» → «Комнаты и права»** создайте комнату, добавьте второго пользователя и выдайте права. Проверьте текст в обе стороны, небольшой файл, скачивание по нажатию и **«Настройки» → «Подключение»** для выбора каждого из двух узлов. Проверка на ПК не заменяет испытание на OpenMANET и радиоканале.
