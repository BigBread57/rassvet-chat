# API первого этапа

Версия протокола: `/v1`. Все запросы идут по HTTPS; JSON использует UTF-8, время — RFC 3339 UTC, идентификаторы — UUID. Клиент доверяет только ключам двух узлов из данных активации. Межузловой API принимает взаимный TLS только от настроенного второго узла. Этот документ задаёт контракт для реализации, а не результат испытания стенда.

## Общие правила

- Обычный запрос содержит `Authorization: Device <user_id>:<device_id>`, `X-Time`, `X-Nonce`, `X-Body-SHA256` и `X-Signature`. Подпись ECDSA P-256/SHA-256 ключом телефона покрывает метод, путь с запросом, значение `Authorization`, время, nonce и hex-хеш точных байтов тела в этом порядке, разделённых переводом строки. `X-Signature` содержит base64 кодирование подписи ASN.1 DER. Узел проверяет привязку, подпись, свежесть времени, однократность nonce и совпадение хеша с фактически принятым телом до публикации данных. Для пустого тела используется SHA-256 пустой строки. Активация — единственное исключение: до неё у телефона нет привязки.
- `GET` не меняет данные. `POST /rooms/{room_id}/presence` фиксирует вход командира. Повтор отправки текста использует тот же `id` сообщения; повтор загрузки вложения — тот же `attachment_id`. Для этих двух операций повтор с прежним содержимым не создаёт вторую запись, а несовпадение содержимого даёт `409`. Общий заголовок `Idempotency-Key` для остальных изменений пока не реализован.
- Списки возвращают `items` и `next_cursor` (`null`, если продолжения нет). `limit` от 1 до 100, по умолчанию 50. Курсор непрозрачен; обычная история сортируется по `(sent_at, id)` по возрастанию. Истёкшие записи в выдачу не попадают.
- Любой успешный ответ с JSON имеет `Content-Type: application/json`. Ошибка: `{"error":{"code":"...","message":"..."}}`. `400 invalid_request`, `401 unauthenticated`, `403 forbidden`, `404 not_found`, `409 conflict`, `413 too_large`, `422 checksum_mismatch`, `429 rate_limited`, `503 unavailable`. Для скрытой комнаты, её истории и вложения постороннему возвращается одинаковый `404 not_found` без названия комнаты и иных закрытых данных. Неизвестная привязка и неверная подпись дают `401`. Запросы изменения отдельного сообщения (`PUT`, `PATCH`, `DELETE`) отсутствуют; для них возвращается `405`.
- Все ограничения тела проверяются до разбора и записи. Предел JSON — 1 МиБ; размер файла задаётся настройкой узла, начально 100 МиБ. `expires_at` вычисляется узлом от `sent_at` по действующему сроку, начально 3 дня.

## Выдача телефона

Начальный администратор создаётся локальной командой установки `init-admin`, которая сразу выдаёт JSON для активации первого телефона (`code`, `issuer`, `nodes`). Если код истёк до привязки, локальная команда `reissue-admin` заменяет его. Публичной регистрации нет.

| Метод и путь | Запрос | Успех | Доступ |
| --- | --- | --- | --- |
| `POST /v1/admin/users` | `{"name":"Анна","role":"user"}`; роль `user`, `admin` или `commander` | `201 {"id":"uuid","name":"Анна","role":"user"}` | Администратор |
| `GET /v1/admin/users` | `?cursor=uuid&limit=50` | `200 {"items":[{"id":"uuid","name":"Анна","role":"user","activated":false}],"next_cursor":null}` | Администратор; список действующих учётных записей; `activated` означает привязанный телефон |
| `DELETE /v1/admin/users/{user_id}` | — | `204` | Администратор; отзывает доступ и скрывает учётную запись, не удаляя историю; свой аккаунт удалить нельзя |
| `POST /v1/admin/users/{user_id}/activation` | `{"ttl_seconds":600}` | `201 {"code":"одноразовый код","expires_at":"...","issuer":"https://...","nodes":[{"url":"https://...","tls_spki_sha256":"base64"}]}`; эти данные кодируются в QR | Администратор; код хранится на узле выдачи |
| `POST /v1/activation` | `{"code":"...","device_id":"uuid","public_key_p256":"base64 DER"}` | `200 {"user_id":"uuid","device_id":"uuid","role":"user","nodes":[...]}` | Только узел выдачи; проверенный TLS по QR; код погашается и привязка создаётся одной транзакцией |
| `GET /v1/me` | — | `200 {"id":"uuid","name":"Анна","role":"user"}` | Активированный телефон |

Истёкший/использованный код и повторная привязка дают `409 conflict`; неверный код — `404 not_found`. Успешная привязка пересылается второму узлу. PIN проверяется локально Android-клиентом до доступа к ключу и истории; сетевого API для PIN нет.

## Комнаты и права

Набор прав участника: `read`, `send_text`, `add_attachment`, `save_attachment`. Администратор назначает их явно. Капитан имеет полный доступ в комнатах, где он состоит и имеет право чтения. Любой ответ с комнатой содержит права, действующие на принявшем узле; узел заново проверяет их на каждом действии.

| Метод и путь | Запрос | Успех | Доступ |
| --- | --- | --- | --- |
| `POST /v1/admin/rooms` | `{"name":"Группа"}` | `201 {"id":"uuid","name":"Группа"}` | Администратор |
| `GET /v1/admin/rooms` | `?cursor=uuid&limit=50` | `200 {"items":[{"id":"uuid","name":"Группа"}],"next_cursor":null}` | Администратор; список всех комнат |
| `PUT /v1/admin/rooms/{room_id}` | `{"name":"Новое имя"}` | `200 {"id":"uuid","name":"Новое имя"}` | Администратор; имя уникально без учёта регистра |
| `PUT /v1/admin/rooms/{room_id}/members/{user_id}` | `{"read":true,"send_text":true,"add_attachment":false,"save_attachment":false}` | `200 {"user_id":"uuid","rights":{...}}` | Администратор |
| `GET /v1/admin/rooms/{room_id}/members` | `?cursor=uuid&limit=50` | `200 {"items":[{"user_id":"uuid","name":"Анна","rights":{"read":true,"send_text":true,"add_attachment":false,"save_attachment":false}}],"next_cursor":null}` | Администратор |
| `DELETE /v1/admin/rooms/{room_id}/members/{user_id}` | — | `204` | Администратор |
| `GET /v1/rooms` | `?cursor=...&limit=50` | `200 {"items":[{"id":"uuid","name":"Группа","rights":{...}}],"next_cursor":null}` | Только доступные комнаты; командиру — все |
| `GET /v1/rooms/{room_id}` | — | `200 {"id":"uuid","name":"Группа","rights":{...},"members":[{"user_id":"uuid","name":"Анна"}]}` | Право `read` или командир |
| `POST /v1/rooms/{room_id}/presence` | `{"kind":"commander_entered"}` | `201 {"id":"uuid","commander_id":"uuid","entered_at":"..."}` | Только командир |
| `GET /v1/rooms/{room_id}/events` | `?cursor=...&limit=50` | `200 {"items":[{"id":"uuid","kind":"commander_entered","commander_id":"uuid","entered_at":"..."}],"next_cursor":null}` | Право `read` или командир |

`GET .../events?latest=1` возвращает последние события и `cursor` для обновлений комнаты; `next_cursor` ведёт к более старым событиям. `GET .../events?since_rowid=<cursor>` возвращает новые записи в порядке их появления на узле, включая поздно доставленные межузловые события. Если обновления не поместились в страницу, клиент продолжает запросом с `next_cursor`.

## Текст и подтверждения

`message_id` создаёт телефон один раз до первой отправки и сохраняет при повторе. Состояние `saved` появляется только в ответе после записи узлом. `delivered` означает отдельное подтверждение получения телефоном адресата; `read` — подтверждение открытия им сообщения. Подтверждения относятся к паре `(message_id, user_id)`; отправителю возвращается список адресатов с их состояниями, а общий статус вычисляется из этих событий.

| Метод и путь | Запрос | Успех | Доступ |
| --- | --- | --- | --- |
| `POST /v1/rooms/{room_id}/messages` | `{"id":"uuid","text":"Привет"}` | `201 {"id":"uuid","room_id":"uuid","sender_id":"uuid","text":"Привет","sent_at":"...","expires_at":"...","state":"saved"}`; повтор того же ID и содержимого возвращает эту запись | `send_text` или командир |
| `GET /v1/rooms/{room_id}/messages` | `?cursor=...&limit=50` | `200 {"items":[{"id":"uuid","sender_id":"uuid","text":"Привет","sent_at":"...","expires_at":"...","receipts":[{"user_id":"uuid","state":"delivered","at":"..."}]}],"next_cursor":null}` | `read` или командир |
| `POST /v1/rooms/{room_id}/messages/{message_id}/receipts` | `{"state":"delivered"}` либо `{"state":"read"}` | `200 {"message_id":"uuid","user_id":"uuid","state":"delivered","at":"..."}` | Адресат с `read` или командир; `read` не понижает состояние |

`GET .../messages?latest=1` возвращает последние `limit` сообщений в порядке `(sent_at, id)` по возрастанию, `cursor` для последующих обновлений и `next_cursor` для загрузки более старой страницы. `GET .../messages?cursor=<next_cursor>` продолжает историю в нужном направлении. `GET .../messages?since_rowid=<cursor>` возвращает новые записи в порядке добавления, включая поздно доставленные сообщения с более ранним `sent_at`; ответ содержит следующий `cursor` и `next_cursor`, если новые записи не поместились в одну страницу. `latest` и `since_rowid` нельзя совмещать с другим режимом выборки.

`receipts_only=1` оставляет в каждой записи истории только `id` и `receipts`, без текста и сведений об отправителе. Клиент запрашивает такие страницы для обновления состояний уже показанных им сообщений; доступ к комнате проверяется так же, как для полной истории.

Узел не принимает редактирование или удаление текста пользователем. Получение истории не считается подтверждением прочтения: клиент отправляет отдельный запрос после открытия.

## Вложения и настройки

Файл передаётся потоком. Заголовки загрузки: `Content-Length`, `X-Content-SHA256` (hex), `X-File-Name` (UTF-8, в метаданных очищается), `Content-Type`. Подпись запроса покрывает SHA-256 файла. Узел пишет временный файл, проверяет фактический размер и хеш, затем атомарно публикует метаданные и файл. Обрыв оставляет только временный файл для уборки.

| Метод и путь | Запрос | Успех | Доступ |
| --- | --- | --- | --- |
| `PUT /v1/rooms/{room_id}/attachments/{attachment_id}` | Поток файла и заголовки выше | `201 {"id":"uuid","room_id":"uuid","name":"photo.jpg","mime_type":"image/jpeg","size":123,"sha256":"hex","sent_at":"...","expires_at":"..."}` | `add_attachment` или командир |
| `GET /v1/rooms/{room_id}/attachments/{attachment_id}` | — | `200` поток; `Content-Length`, `Content-Type`, `X-Content-SHA256` | `read` или командир; проверка на каждом запросе |
| `GET /v1/rooms/{room_id}/attachments` | `?cursor=...&limit=50` | `200 {"items":[{"id":"uuid","name":"photo.jpg","size":123,"sha256":"hex","expires_at":"..."}],"next_cursor":null}` | `read` или командир; тело файлов не выдаётся |
| `GET /v1/admin/settings` | — | `200 {"attachment_max_bytes":104857600,"retention_seconds":259200}` | Администратор |
| `PUT /v1/admin/settings` | `{"attachment_max_bytes":104857600,"retention_seconds":259200}` | `200` с действующими настройками | Администратор |

`GET .../attachments?latest=1` возвращает последние метаданные, `cursor` для обновлений и `next_cursor` для старых страниц. `GET .../attachments?since_rowid=<cursor>` возвращает новые метаданные в порядке их появления на узле, включая поздно доставленные со второго узла; при переполнении страницы клиент продолжает с `next_cursor`. Эти запросы не передают содержимое файлов.

Превышение предела даёт `413`, несовпадение хеша — `422`; в обоих случаях публикации нет. Android загружает тело только после нажатия и проверяет хеш. При праве `save_attachment` файл автоматически сохраняется в системные «Загрузки», а после загрузки показывается одна кнопка «Передать». Без этого права файл остаётся только в управляемом кеше приложения. Истёкшие файл и метаданные не выдаются и удаляются на узлах и из управляемого кеша клиента.

`retention_seconds` принимает значения от 1 до 9223372036 секунд; большее число отклоняется, чтобы расчёт срока в Go не переполнял `time.Duration`. `attachment_max_bytes` принимает значения от 1 до 104857600 байт. Оба ограничения действуют и для настроек, полученных от второго узла.

## Обмен двух узлов

Пути `/v1/peer/*` требуют взаимного TLS с сертификатом настроенного второго узла. Неизвестный сертификат отклоняется при TLS handshake. События содержат глобальный ID, автора, время и полезную нагрузку; в базе действует уникальность ID. Узел подтверждает приём только после локальной записи. Повтор события с тем же ID и содержимым возвращает прежнее подтверждение; конфликт содержимого даёт `409`. Истёкшие данные не передаются.

| Метод и путь | Запрос | Успех |
| --- | --- | --- |
| `GET /v1/peer/health` | — | `200 {"node_id":"uuid","protocol":1}` |
| `GET /v1/peer/events` | `?cursor=...&limit=100` | `200 {"items":[{"id":"uuid","kind":"user|binding|room|room_rename|rights|message|receipt|presence|settings|attachment","author_node_id":"node-a","created_at":"...","payload":{...}}],"cursor":"123","next_cursor":null}`; `cursor` сохраняется после записи всех событий страницы |
| `POST /v1/peer/events` | `{"events":[{"id":"uuid","kind":"message","author_node_id":"node-a","created_at":"...","payload":{...}}]}` | `200 {"accepted":["uuid"],"cursor":"..."}` |
| `GET /v1/peer/attachments/{attachment_id}` | — | `200` поток с `Content-Length` и `X-Content-SHA256` |
| `PUT /v1/peer/attachments/{attachment_id}` | Поток с `Content-Length` и `X-Content-SHA256` | `201 {"id":"uuid","size":123,"sha256":"hex"}` |

При действующей связи узлы повторно запрашивают недостающие события по курсору; повтор не создаёт вторую запись. Повтор идентификатора пользователя, привязки, комнаты или входа командира с другим содержимым отклоняется как конфликт, а не пропускается молча. Вложение передаётся потоком и записывается на втором узле только после проверки размера и SHA-256; затем публикуются метаданные. Настройка ровно двух адресов и доверенных сертификатов задаётся при установке.

## Покрытие спецификаций

| Спецификация | Сценарии и запросы |
| --- | --- |
| `device-provisioning` | Саморегистрация: анонимный `POST /admin/users` → `401`; первая/вторая активация: `POST /activation` → `200`/`409`; неверный PIN блокирует локальный клиент без запроса; подмена узла отклоняется проверкой TLS до запроса. |
| `room-access` | Чужая комната: `GET /rooms`, `GET /rooms/{id}` → отсутствие/`404`; прямой запрос без права: `POST /rooms/{id}/messages` → `403`; вход командира: `GET /rooms/{id}` и `POST /rooms/{id}/presence` → `200`/`201`, участники получают событие через `GET /rooms/{id}/events`. |
| `room-messaging` | Обмен: `POST /rooms/{id}/messages`, `GET /rooms/{id}/messages`, `/peer/events`; состояния: `POST /rooms/{id}/messages/{message_id}/receipts` и история; редактирование: `PUT /rooms/{id}/messages/{message_id}` → `405`; истечение: история → пустой список. |
| `room-attachments` | Предел/целостность: `PUT /rooms/{id}/attachments/{id}` → `413`/`422`; чужая ссылка: `GET /rooms/{id}/attachments/{id}` → `404`; список метаданных без тела: `GET /rooms/{id}/attachments`; скачивание по нажатию: `GET /rooms/{id}/attachments/{id}`; сохранение зависит от `save_attachment`; истечение: `GET` → `404`. |
| `two-node-delivery` | Клиенты на разных узлах: локальные `GET /rooms/{id}/messages` после `/peer/events`; повтор события → один ID; неизвестный узел отклоняется TLS до `/peer/events`. |
